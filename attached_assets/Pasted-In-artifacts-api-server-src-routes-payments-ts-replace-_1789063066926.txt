In artifacts/api-server/src/routes/payments.ts, replace autoGenerateFee and
its 5%-rule constants with the confirmed flat-fee rule.

1. Replace INTERIM_FEE_RULE / INTERIM_FEE_RATE with:
   const FEE_RULE = "alta_flat_160_per_client_month";
   const ALTA_FLAT_FEE_AMOUNT = "160.00"; // set by Alta; flat, not a % of the payment

2. Replace autoGenerateFee with a reconciliation helper —
   reconcileMonthlyFee(clientId, feeMonth, triggeringPaymentId, userId, tx) —
   that makes the fee state for that (client, month) match reality rather
   than just inserting:
   a. Count non-deleted Payments for this clientId + paymentMonth = feeMonth
      where paymentType IN ('direct_payment', 'reimbursement'). Explicitly
      exclude paymentType = 'fee' — a fee payment must never count toward or
      trigger another fee. (This is also a bug fix: today autoGenerateFee
      runs unconditionally for every payment type, including 'fee' payments,
      so a logged Fee payment currently generates a second cascading fee on
      itself. That stops here.)
   b. If the count is > 0: look for an existing non-deleted Fee for
      (clientId, feeMonth). If none exists, insert one — amount
      ALTA_FLAT_FEE_AMOUNT, ruleApplied FEE_RULE, status 'pending', clientId,
      feeMonth, paymentId = triggeringPaymentId — and audit-log
      "auto_generate_fee". If one already exists, do nothing (idempotent —
      don't touch its amount or status). Guard the race the same way the
      duplicate-payment check does: take a pg_advisory_xact_lock keyed on
      hashtext(clientId:feeMonth) before the SELECT-then-INSERT, inside the
      same transaction as the payment write.
   c. If the count is 0 (this only happens when called from an edit/delete
      that just removed the last qualifying payment from the month — see
      Prompt 3): find the active Fee for (clientId, feeMonth). If it exists
      AND ruleApplied === FEE_RULE (still the auto rule, never manually
      adjusted) AND status === 'pending' (never invoiced, collected, or
      waived) — soft-delete it and audit-log "auto_reverse_fee" with a
      message like "No qualifying payment remains for <clientId> / <month>."
      Otherwise leave it completely alone; this must never silently undo a
      fee staff has already progressed or manually corrected.

3. Call reconcileMonthlyFee from POST /payments (after insert) when the new
   payment's paymentType is direct_payment or reimbursement and paymentMonth
   is set (reuse the same checkDate → paymentMonth derivation this route
   already does for the duplicate check, so a payment missing an explicit
   month still resolves one from checkDate). Do NOT call it for paymentType
   'fee', or when paymentMonth can't be resolved at all — flag that last case
   in the PR as a [CONFIRM]: should logging a direct_payment/reimbursement
   with literally no derivable month be blocked outright, or just silently
   skip fee generation? Recommend treating it the same as today (allowed,
   just doesn't derive a month) since this is an existing edge case, not new.

   payments.test.ts to cover the new flat rule: first qualifying payment in a
   client-month creates exactly one $160 fee; a second qualifying payment in
   the same client-month does not create a second one; a 'fee'-type payment
