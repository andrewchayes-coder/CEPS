In the CEPS app, invoices and payments currently each carry a single
`serviceMonth` and a single `authorizationId` — one invoice or payment can
only ever represent one month against one authorization. In practice an
invoice can span multiple months, and a single vendor bill can cover several
line items against different authorizations (e.g. monthly fee + registration
fee + admin fee, each authorized separately). Payments have the identical
limitation. Replace the single-value fields with a real line-items model on
both sides, reusing the many-to-many allocation pattern already proven out in
this codebase for remittances (`remittance_allocations`).

1. Add an `invoice_line_items` table: `id`, `invoiceId` (FK to `invoices`,
   cascade delete), `authorizationId` (FK to `authorizations`, required),
   `serviceMonth` (text, `YYYY-MM`, required), `amount` (numeric), `createdAt`.
   An invoice covering 3 months against one authorization is 3 line items
   (same authorizationId, different serviceMonth); an invoice covering 3
   different authorizations for the same month is 3 line items (same
   serviceMonth, different authorizationId). No soft-delete needed on this
   table — editing an invoice's line items replaces the full set for that
   invoice transactionally, the same way the existing invoice edit flow
   already replaces other fields wholesale.

2. Migrate existing data: for every existing invoice row, create exactly one
   `invoice_line_items` row from its current `authorizationId` /
   `serviceMonth` / `amountRequested`. Leave the `invoices.authorizationId`
   and `invoices.serviceMonth` columns in place but stop writing to them going
   forward — same treatment already used elsewhere in this codebase for
   deprecated-but-not-dropped columns (see the `clients.familyRep*` columns
   from the Family Representatives migration for the pattern to follow).
   `invoices.amountRequested` becomes a derived total: always the sum of its
   line items' amounts, recomputed on save.

3. Update the invoice create and edit screens to manage a dynamic list of
   line items instead of single Service Month / Authorization fields: each
   row has an Authorization picker (scoped to the invoice's client, same
   searchable-select component already used elsewhere), a Service Month
   input, and an Amount. Support adding and removing rows, require at least
   one, and show the invoice total as the read-only sum of all rows. Reject
   save if that sum doesn't reconcile with what's submitted (guard against
   silent drift, the same way remittance_allocations already guards against
   over-allocation).

4. Add a `payment_allocations` table with the same shape and constraints as
   `remittance_allocations` (`paymentId` FK cascade delete, `authorizationId`
   FK cascade delete, `amount`, `autoMatched` not needed here, unique pair,
   positive-amount check). This lets one payment (one check) be split across
   more than one authorization's budget, mirroring the invoice-side change.
   Migrate existing data the same way: one `payment_allocations` row per
   existing payment from its current `authorizationId` / `amount`. Leave
   `payments.authorizationId` in place but deprecated going forward.

5. Update Log Payment and Edit Payment to manage allocations instead of a
   single Authorization field: when an invoice is selected, default one
   allocation row per that invoice's line items (authorization + amount
   pre-filled from the line item, editable); without an invoice selected,
   allow manually adding one or more authorization allocations directly.
   Payment total = sum of allocations, validated the same way as invoices.

6. This is the part most likely to silently break something if missed:
   audit and update every place that currently reads `payments.authorizationId`
   directly to sum or filter payment totals, and repoint it at
   `payment_allocations` instead. The two confirmed today are
   `authorizationTotalsPaid()` in `lib/serializers.ts` (the exact per-authorization
   paid-total sum used on authorization detail/list) and the `totalPaidSql` /
   effective-status CASE expression in the authorizations list/search route
   (drives "exhausted" status and remaining-amount calculations). Also check
   the vendor-payment report, expiring-authorization report, and any other
   report or dashboard tile that aggregates payments by authorization — treat
   every remaining `payments.authorizationId` reference as suspect until
   confirmed it's still correct post-migration.

Write tests covering: an invoice with 3 line items across 2 authorizations
and 2 service months saves and reloads correctly with the right computed
total; a payment allocated across 2 authorizations correctly increases both
authorizations' totalPaid/remaining-amount, and can push one of them into
"exhausted" while leaving the other unaffected; migrating an existing
single-authorization invoice and payment produces exactly one line
item/allocation each with matching values (no data loss on the migration);
and over-allocating a payment beyond its total amount is rejected, mirroring
the existing remittance_allocations over-allocation guard.
