In the CEPS app, make three related changes to how authorizations (POS records) are tracked.

1. Auto-derive "pending" status and remove manual status editing.
   Today `authorizations.status` is a plain manually-set column, and the list/detail
   endpoints already compute an *effective* status server-side that overrides the
   stored value for "expired" (service period end date has passed) and "exhausted"
   (total paid >= max period amount) — but NOT for "pending". Extend that same
   derivation logic (find it in the authorizations list/search route where the
   effective-status SQL case expression lives) so that an authorization whose
   service period start date is in the future is also always shown as "pending",
   regardless of the stored status value. Once that's in place, remove the Status
   dropdown from the Edit Authorization dialog entirely — status becomes fully
   computed (active / expired / pending / exhausted) with no manual override
   anywhere in the UI. Keep the stored `status` column as-is for now (used
   internally), just stop exposing it as an editable field.

2. Make Max Period Amount editable on an existing authorization.
   The Create Authorization screen already has an editable Max Period Amount
   field (auto-filled from the parsed POS PDF, but editable). The Edit
   Authorization dialog has no such field at all — once an authorization is
   created, its max amount is frozen. Add a Max Period Amount field to the Edit
   Authorization dialog, same input treatment as the create screen (currency
   input, freely editable by staff), so a mid-authorization price change or a
   fiscal-year-boundary correction can be captured after the fact.

3. Add authorization version history.
   When a revised POS comes in for an authorization that already exists (price
   adjustment, date change, cancellation, or simply a duplicate/reissue), staff
   need to see prior versions, not just the current values. Add a new table
   (e.g. `authorization_versions`) that snapshots the full authorization row —
   including which POS PDF it came from and its received date — every time an
   authorization is edited. Add a "Version History" section to the authorization
   detail page showing each snapshot in reverse-chronological order (received
   date, who/what changed, and a link to that version's POS PDF if present).
   The live `authorizations` row keeps driving all downstream logic (payments,
   remaining-amount calculations, effective status) exactly as today — this is
   an audit/reference trail, not a new source of truth. Do not add a UI action
   that's just "edit a typo" vs. "record a new POS version" as separate flows
   unless it's trivial — a version snapshot on every save is fine and simpler.

Write tests covering: the pending-derivation SQL change (auth with a future
start date shows as pending regardless of stored status), that Max Period
Amount updates persist and are reflected in remaining-amount calculations, and
that editing an authorization creates a version snapshot without altering the
live row's other invariants (soft-delete, role-scoping, etc.).
