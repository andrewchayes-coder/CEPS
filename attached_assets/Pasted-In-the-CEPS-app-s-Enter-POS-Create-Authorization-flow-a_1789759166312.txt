In the CEPS app's Enter POS (Create Authorization) flow, a revised or amended
POS for an authorization that already exists currently just creates a brand
new authorization row — there's no check for an existing match first. Fix
this so an amendment updates the existing authorization in place instead.

1. Once the client and authorization number are both known on the Enter POS
   screen (whether typed manually or filled from the PDF parser), check for
   an existing non-deleted authorization for that exact (clientId, authNumber)
   pair before submitting.

2. If no match is found, behave exactly as today (create a new authorization).

3. If a match IS found, switch the screen into an "Amend Authorization" mode
   instead of attempting a plain create (which would otherwise collide with
   the existing `authorizations_client_id_auth_number_unique` constraint and
   fail). Show the existing authorization's Start Date, End Date, Monthly
   Amount, and Max Period Amount side by side with the newly entered/parsed
   values, clearly highlighting which fields differ. Require explicit staff
   confirmation before applying — don't silently overwrite.

4. On confirmation, snapshot the authorization's current (pre-amendment)
   values into `authorization_versions` (the table added this morning for
   version history) and then update the live authorization row's Start Date,
   End Date, Monthly Amount, and Max Period Amount to the new values. Don't
   write a separate status value for active/expired/pending/exhausted — the
   effective-status derivation already in place picks up the new
   dates/amounts automatically on the next read.

5. Also capture the POS document's own notes/footer text (where Alta's
   accounting team records adjustment details) as a new text field on the
   authorization — e.g. `posNotes` — updated on every amendment the same way
   the four numeric/date fields are, and shown during the amend confirmation
   step alongside the diffed values. Don't try to parse or interpret this
   text — just extract and store it verbatim from the PDF the same way the
   other parsed fields already are, so it's not lost when a revised POS
   comes in.

6. Add "canceled" as a fifth valid authorization status, alongside the
   existing active/expired/pending/exhausted. Do NOT try to infer a
   cancellation automatically from an amended POS's data — the rule for
   detecting that is explicitly still undecided (pending a follow-up
   discussion). Instead, add a distinct, deliberate "Cancel Authorization"
   staff action (separate from the amend flow above, and separate from the
   status dropdown that was already removed this morning) that sets status
   to "canceled" directly, with a required reason/note, logged as its own
   audit action. This keeps "canceled" reachable today without guessing at
   logic that isn't settled yet.

7. Log the amendment itself as its own audit action (e.g.
   "amend_authorization") distinct from a plain edit, so the audit trail
   shows it was recorded as a POS amendment rather than a routine field
   correction.

Write tests covering: submitting a POS for a brand-new (client, authNumber)
pair still creates a new authorization as before; submitting one that
matches an existing non-deleted authorization triggers the amend flow instead
of a create attempt; confirming an amendment creates exactly one new
`authorization_versions` snapshot of the prior values, updates the live row
including `posNotes`, and does not touch status directly; a soft-deleted
authorization with the same (client, authNumber) does NOT block a fresh
create (matching the existing partial-unique-index behavior); and the manual
Cancel Authorization action sets status to "canceled" with a required reason
and its own audit entry.
