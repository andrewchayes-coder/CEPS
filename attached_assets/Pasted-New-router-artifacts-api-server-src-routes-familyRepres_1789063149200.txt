New router artifacts/api-server/src/routes/familyRepresentatives.ts, mounted
alongside the other route files (follow clients.ts's requireAuth/requireStaff
import pattern), plus small edits to invites.ts and referrals.ts.

FAMILY-REP CRUD (familyRepresentatives.ts):
1. GET /family-representatives?clientId=<id> — requireAuth. Staff/coordinator
   can query any clientId. A parent_guardian/self user can only list their
   OWN linked client's reps (reuse the scopeClientId() pattern already in
   clients.ts — if a clientId query param is passed by a family user, it must
   equal their own linked client, else 403). Returns non-deleted rows for
   that client, each including a resolved `hasPortalAccount` /
   `portalAccountStatus` field: 'none' (userId null, no pending invite),
   'invited' (a non-expired, unused invite magic_link references this
   familyRepresentativeId), or 'active' (userId set). Order isPrimary desc,
   then name.

2. POST /family-representatives — requireStaff only. Body: clientId, name
   (required), relationship, phone, email, address, isPrimary. Validate the
   client exists and isn't deleted. Audit-log "create_family_representative".

3. PATCH /family-representatives/:id — requireAuth.
   - Staff: can edit any field on any row (including isPrimary, but not
     clientId or userId — those aren't user-editable).
   - parent_guardian/self: can edit ONLY the row where row.userId equals
     their own user id, and ONLY name/relationship/phone/email/address (not
     isPrimary, clientId, or userId). Anyone else's row, or any field outside
     that set, is a 403 — mirror the exact error-shape pattern
     PATCH /clients/:id already uses for its FAMILY_EDITABLE_FIELDS check.
   Audit-log "update_family_representative" with a diff (reuse diffDetail
   from lib/serializers.ts, same as clients.ts).

4. DELETE /family-representatives/:id — requireStaff only. Soft-delete the
   row. If it has a non-null userId, ALSO deactivate that user account
   (users.active = false) in the same transaction — removing a family rep
   must actually revoke their portal access, not just hide the contact card,
   mirroring how deactivating a vendor already works elsewhere in this repo.
   Audit-log both the delete and the cascade deactivation.

TESTS: cover each role's access boundary above (staff full CRUD; a family
user editing their own row succeeds; editing someone else's row or a
disallowed field 403s; delete cascades to deactivate the linked user).

INVITE LINKAGE (invites.ts):
5. Extend CreateInviteBody with an optional `familyRepresentativeId`. When
   present, validate it exists, isn't deleted, and belongs to the same client
   as `linkedRecordId` (role must be parent_guardian or self,
   linkedRecordType 'client') — store it on the created magic_links row.
6. In the accept-invite handler, when the accepted magic_link has a
   familyRepresentativeId, set that family_representatives row's userId to
   the newly created user's id (same transaction as account creation).

TESTS: accepting an invite created with a familyRepresentativeId links the
row to the new user; an invite without one behaves exactly as it does today
(no regression for vendor/plain parent invites).

INTAKE RECIPIENT BY SPECIFIC PERSON (referrals.ts):
7. POST /referrals/:id/send-intake currently takes
   `recipient: 'participant' | 'family_rep'` and resolves the email via
   client.email or client.familyRepEmail. Change the family-rep case: when
   recipient is 'family_rep', ALSO require `familyRepresentativeId` in the
   body. Validate it belongs to this referral's client and has a non-blank
   email (400 with a clear message if not — same pattern as today's "add
   that email to the record first" error). Persist BOTH `intakeSentTo:
   'family_rep'` and the new `intakeSentToFamilyRepId` on the referral. The
   'participant' recipient case is unchanged (still blocked when
   client.isMinor is true — that requirement doesn't change, only who else
   can also get access changes).
8. GET /signature/:token (the signing-page payload builder): when
   referral.intakeSentTo is 'family_rep', pull the displayed
   parent/guardian/conservator name/relationship/phone/email from the
   family_representatives row referenced by intakeSentToFamilyRepId instead
   of client.familyRepName/familyRepEmail. Leave the 'participant' branch
   unchanged.

TESTS: sending an intake to a family rep without familyRepresentativeId
400s; sending to a rep with no email on file 400s; a successful send persists
intakeSentToFamilyRepId; the signature payload reflects that specific rep's
name/relationship, not a different rep on the same client.
