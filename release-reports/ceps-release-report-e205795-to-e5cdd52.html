Executive summary

This release candidate materially improves staff data operations and financial reconciliation while making everyday lists easier to navigate. The largest changes are the finalized Alta payment/remittance imports, the new allocation ledger for partial remittance matching, secure staff referral reassignment, participant/family remittance actions, and consistent sortable tables.

Faster day-to-day navigation

Staff-facing lists and reports now use accessible sorting, stable tie-breaks, and server-side sort parameters where pagination requires them. User-facing wording consistently says Participant, while internal API/database identifiers remain unchanged.

Trace: dc4bd2b, 5726c6c · portal table/page files; API sorting.ts and list routes

Confirmed Alta import workflows

Payments now use the Alta FMS Transaction Detail by Account Excel format; remittances use the Payment History Detail Report summary/detail CSV. Server validation, natural-key matching, source fingerprints, duplicate reporting, and audit behavior are preserved.

Trace: ccf70e3, 119e47f, 4b1c93e, e5cdd52 · Alta parsers, payment routes, import dialogs

Safer reconciliation

A remittance can be allocated across one or more eligible payments, and a payment can receive more than one remittance allocation. Transactional balance checks prevent either side from being over-applied. Existing one-to-one matches are backfilled into the allocation ledger.

Trace: 90805a0 · payments/remittances API, serializers, schema, migration 0007

Stronger staff workflows

Staff can create and update vendors, reassign referrals only to active service coordinators, and review or match participant-submitted remittances. Correction-only CSV downloads help resolve Alta errors without exporting successful rows or internal IDs.

Trace: 035a818, f6bacb0, 13d1613

Portal behavior changes

Tables, reports, and audit history

  • Sortable headers were added across participants, authorizations, invoices, payments, referrals, users, vendors, remittances, the audit log, dashboard summaries, and operational reports. Server-backed tables reset pagination when sorting changes and apply deterministic secondary ordering.
  • Report tables support local sorting where their data is already fully loaded. The audit-log export preserves the active sort order while fetching all filtered pages.
  • Participant and vendor names are linked to their record pages for authorized roles; restricted-role views preserve plain text where navigation is not allowed.
Representative paths: artifacts/ceps-portal/src/components/ui/table.tsx, src/lib/table-sorting.ts, src/pages/audit-log.tsx, src/pages/reports.tsx; API list routes and src/lib/sorting.ts.

Participant terminology

User-visible labels, search prompts, empty states, and report metrics now use “Participant.” This is a presentation change, not a data-model migration: source code, API contracts, and database tables still use the existing client identifiers.

Vendor and referral administration

  • Staff can create vendors and update business profiles. The API trims values, rejects blank business names, reports duplicate names as conflicts, and audits successful mutations.
  • Referral editing supports staff reassignment to an active service coordinator. Coordinators cannot reassign referrals themselves, and existing ownership-based access checks remain in force.

Analytics instrumentation

Lightweight Umami events were added for meaningful portal interactions, including imports and correction-report downloads. Tracking is intentionally non-blocking and no-ops when Umami is unavailable. This range does not add an analytics dashboard, warehouse pipeline, or guaranteed external delivery.

Trace: 24fa755 · artifacts/ceps-portal/src/lib/analytics.ts and instrumented pages/components.

Alta payments and remittances

Alta FMS payment workbooks

  • The Payments Log accepts the confirmed Alta FMS Transaction Detail by Account .xlsx workbook and extracts its first worksheet in the browser; authoritative interpretation remains on the API.
  • Only Check rows are processed. Participants resolve by the trailing seven-digit UCI in Customer; authorization and service month resolve from Description.
  • Historical imports use source historical_import and do not create CEPS fee records. Repeated check numbers are allowed because one check may represent multiple monthly lines.
  • Identical source rows are skipped by SHA-256 source fingerprint. An existing participant/authorization/service-month payment is held as a business duplicate rather than silently inserted.
  • Lookup queries are scoped to keys in the workbook and chunked to stay under database parameter limits for exceptionally large files.

Alta Payment History Detail Reports

  • The parser requires the report summary Date, positive Amount, and Reference #, then applies the summary date/reference to each detail row.
  • Each detail row requires UCI, Auth #, Service M/Y, and positive Amount. The complete detail total must exactly reconcile to the summary Amount before any rows import.
  • Rows may auto-match, require manual matching, be skipped as exact duplicates, or be rejected with a correction reason. Batch identifiers and report references remain distinct.
  • Correction downloads include only errored/held rows and safe row-level detail; they omit successfully imported rows and internal database IDs.
Operational meaning: these workflows record and reconcile financial records. They do not initiate bank transfers or settle payments. No April 1, 2026 cutoff is enforced by the import code.

API and business-workflow changes

  • List endpoints: new sortBy/sortDirection options and deterministic secondary keys support stable server pagination across the main entities and reports.
  • Payments: dedicated Alta FMS import contracts replace the legacy generic check-register path; duplicate locking and source-fingerprint idempotency protect concurrent imports.
  • Remittances: responses expose allocation, allocated amount, and remaining amount; create/update/match operations validate participant ownership, authorization/service month, and remaining balances inside transactions.
  • Referrals: the update contract supports nullable coordinator assignment with server-side role and active-account validation.
  • Vendors: staff-only create/update routes add conflict handling and audit records while preserving existing contact and W-9 behavior.
  • Generated contracts: OpenAPI remains the source of truth; React client and Zod outputs were regenerated for sorting, Alta import outcomes, remittance allocations, referrals, and vendors.

Adds report_reference, review_reason, and expected_amount numeric(12,2) to remittances. No default or backfill is required.

Introduced by ccf70e3.
0007 · Remittance allocation ledger0007_omniscient_ken_ellis.sql
New tableData backfillForeign keys

Creates remittance_allocations with amount, auto-match flag, indexed remittance/payment foreign keys, and one row per remittance/payment pair. It backfills existing non-deleted remittances that have matched_payment_id, using ON CONFLICT DO NOTHING. The legacy matched-payment column remains for compatibility.

Introduced by 90805a0.
0008 · Payment import identity0008_superb_chimera.sql
Index replacementNew nullable column

Drops the unique check-number index, adds nullable source_row_fingerprint, creates a normal check-number index, and creates a partial unique fingerprint index for non-null values. This permits repeated check numbers while making imported source rows idempotent.

Introduced by 119e47f.
Publish-time rule: do not add or run db:migrate as a production startup/deploy command. Development uses checked-in Drizzle migrations; Replit Publish compares development and production schemas and applies the production schema sync. Prior deploy-time migration replay caused duplicate-index failures after Publish had already synchronized schema objects.

Dependencies, configuration, and operations

  • read-excel-file@9.3.10 is a new portal runtime dependency for first-worksheet extraction. The API remains authoritative for Alta business parsing.
  • @playwright/test@1.62.1 and portal test scripts support sorting, participant-language/link, and Alta upload browser regressions. /test-results is ignored for new files.
  • Packaging cleanup: artifacts/ceps-portal/test-results/.last-run.json was already tracked and remains in this candidate; Git ignore rules do not untrack existing files. It contains test metadata, not participant data or production behavior, and should be removed before publish.
  • The API test command is serialized with --maxWorkers=1 to reduce shared-database test collisions and resource pressure.
  • .replit and deployment routing are unchanged in this range. No email provider, storage configuration, or production secret was added.

Regression coverage and verification status

The range adds or expands API coverage for Alta parsing/imports, payment duplicate behavior, payment list behavior, remittance allocation/reconciliation, referral reassignment, vendor mutations, and sorting. Portal Playwright coverage includes table sorting, participant wording and record links, remittance/vendor workflows, and synthetic Alta file uploads with intercepted writes.

Evidence boundary: Git proves that these tests and fixtures are included; it does not, by itself, certify that the complete candidate passed in the production-like environment. Synthetic fixtures contain no real participant data and the Alta browser test intercepts writes.

Recommended release-candidate checks

  1. Run the full API test suite serially and both API/portal typechecks from a clean install.
  2. Run the portal production build and the sorting, participant, Alta upload, remittance, and vendor browser suites against the candidate.
  3. Regenerate API clients from lib/api-spec/openapi.yaml and require a clean diff to catch contract/codegen drift.
  4. Apply migrations to a clean development database and verify remittance backfill/allocation invariants.
  5. Confirm no real Alta files, participant data, secrets, test-results, or unrelated working-tree content are included in the publish.

Known assumptions and decisions still open

This release report does not convert existing open decisions into approvals. Before go-live, CEPS should separately resolve or accept the documented interim behavior for:

  • Transactional email provider and real email delivery (current signature/magic-link workflow still exposes development links where documented).
  • Brand font licensing, exact UCI format/uniqueness rules, e-signature legal sufficiency, vendor W-9 collection, and Phase 2 1099 delivery.
  • The interim 5% fee auto-generation rule for manually logged payments. Historical Alta imports intentionally do not generate fees.
  • Role visibility/security acceptance for participants, invoices, payments, referral reassignment, vendor information, and analytics payloads.
Source: docs/CEPS_OPEN_ITEMS.md as changed in this range. Confirmed Alta source layouts are recorded there; the other listed decisions remain open.
